# 29 · 금화로 조작하는 Joker’s Mate — 플레이 화면 재설계안

**상태: 검토용 화면·조작 설계. 아직 구현하지 않은 제안을 포함한다.**

검토 기준은 `50b95a7`이다. 이번 작업은 설계 문서 작성이며, 애플리케이션·게임 규칙·그림 자산을 수정하지 않는다. 화면 구성은 [30 · ASCII 와이어프레임](30_SCREEN_WIREFRAMES.md)과 함께 본다.

## 1. 제안의 중심

**판을 보고 → 금화를 고르고 → 행동을 확정하고 → 결과를 지켜보는 흐름**으로 만든다.

- 모바일과 데스크톱 모두 숫자 입력창을 없앤다. `10 / 20 / 50 / 100G` 금화 버튼으로 베팅을 준비한다.
- 금화를 누르는 동안은 내 앞의 받침에만 쌓인다. 실제 지출은 금액이 적힌 행동 버튼을 눌렀을 때 한 번 발생한다.
- 체크/콜·폴드·베팅 버튼은 내 차례에 항상 보인다. 레이즈를 찾으려고 메뉴나 접힌 설명을 먼저 열지 않는다.
- 화면의 가장 큰 영역은 체스판 또는 두 사람의 패다. 설명문·거래 내역은 도움말과 기록 안에 둔다.
- 정원·펜화·양피지·체카드 미술은 유지한다. 현대 카지노 칩이나 네온 테이블로 바꾸지 않는다.
- 새로운 공동 카드, 블라인드, 시간제한, 점수 배수, 경제 보정은 넣지 않는다.

## 2. 현재 화면이 조작하기 어려운 이유

최근 시작 화면과 모바일 하단 조작부는 정리되었지만, 다음 문제는 남아 있다.

| 확인한 문제 | 플레이 경험에 미치는 영향 | 설계 결정 |
|---|---|---|
| `main.tsx`의 `type="number"`와 `raise-options` | 공격적 행동이 접힌 영역 안에 있고, 키보드를 열어 누적 투입액을 입력해야 한다 | 항상 보이는 금화 선택 줄과 베팅 확정 버튼 |
| 입력값이 `raise - chessShare`, 실제 실행은 누적 `amount` | “이번에 얼마가 나가는지”를 사용자가 계산한다 | 모든 행동 버튼은 **지금 금고에서 빠질 금액**으로 표시 |
| 판·팟·규칙·족보·잔액이 여러 패널에 반복된다 | 화면을 읽느라 카드와 다음 행동을 놓친다 | 상태 1줄, 중앙 팟 1개, 내 금고 1곳, 행동 영역 1곳 |
| 하단 고정 패널과 카드 영역을 서로 다른 높이 계산으로 보정한다 | 화면 높이에 따라 카드 가림이나 지나친 축소가 재발한다 | HUD / 장면 / 행동 영역이 공간을 나눠 쓰는 레이아웃 |
| 데스크톱 축소용 `zoom`과 모바일 전용 규칙이 공존한다 | 버튼·카드 글자가 함께 작아지고 기기별 결과가 달라진다 | 모바일·가로 화면·데스크톱을 각각 배치하되 조작 의미는 동일하게 유지 |
| 전체 캐릭터 필터와 카드 공개 효과를 함께 적용했던 이력 | 흑 캐릭터의 공개 카드까지 어두워지거나 잘린다 | 캐릭터 진영색, 카드 면, 공개 표시를 독립된 표시 계층으로 취급 |
| 설명이 시작 전부터 필요한 것과 나중에 찾아볼 것을 구분하지 않는다 | 시작 전에 학습을 강요받는 느낌이 난다 | 바로 시작 + 첫 행동에서 짧은 안내 + 선택형 도움말 |

게임성을 높이는 우선순위는 **행동 발견성 → 금액 이해 → 즉각적인 피드백 → 공개의 긴장감 → 장식 연출**이다. 긴 설명을 새 애니메이션으로 덮는 방식은 피한다.

## 3. 다른 게임에서 확인한 패턴과 적용 범위

### 직접 확인한 공개 자료

| 참고 | 확인한 구성 | 이 게임에 적용 | 가져오지 않는 요소 |
|---|---|---|---|
| **PokerTH** 공개 Qt 테이블 정의 [S1] | `BetRaise`, `CallCheck`, `Fold`, `AllIn` 행동 버튼, 33%/50%/100% 팟 버튼, 별도 팟 표시 | 금액 선택과 행동 확정의 구분, 행동 위치 고정, 큰 금액을 빠르게 준비하는 보조 선택 | 텍사스 홀덤 공동 카드·블라인드·여러 좌석·채팅·숫자 입력창 |
| **Lichess** 대국 테이블 코드 [S2] | 플레이 중/종료 후 조작 구분, 상하 플레이어 표시, 메뉴·기록·아이콘 조작, 가능한 상태에 따른 활성화 | 판의 우선순위, 짧은 차례 표시, 상황에 맞는 행동, 보조 기능은 메뉴로 | 체스 시계, 합의 무승부·기권·무르기 등 이 게임에 없는 행동 |

PokerTH 자료는 저장소의 Qt 폼 정의이며 최신 출시 앱의 모든 화면을 실기기로 확인한 것은 아니다. Lichess는 실제 공개 소스의 구성과 상태 처리를 확인했다. 외부 코드를 복사하지 않는다.

PokerStars 기능 페이지, Chess.com 컴퓨터 대국, Balatro 공식 사이트에도 접근을 시도했으나 이 환경의 네트워크 정책에서 403으로 차단되었다. 따라서 이들의 최신 화면·정확한 버튼 배치·공개 타이밍을 직접 관찰한 것으로 서술하지 않는다. 아래 공개 간격과 터치 크기는 **본 프로젝트의 설계 목표**이며 다른 제품의 실측값이 아니다.

### 우리 게임에 맞는 해석

1. 포커의 빠른 금액 선택을 **왕실 금화 묶음**으로 표현한다. `(10G)` 버튼 하나는 10G를 더 올리는 선택이며, 경제 규칙상 새로운 화폐 단위가 생기는 것은 아니다.
2. 체스는 판 위 조작으로 끝낸다. 기물 선택·이동 가능 칸·선택한 기물 정보만 즉시 보여준다.
3. 포커는 **접근 가능한 금화 선택 + 세 가지 행동 위치**를 고정한다. 진행 상태에 따라 합법성·금액·강조만 바꾼다.
4. 공개·승패·정산은 서로 다른 순간이다. 결과를 계산한 시점에 정산창이 판을 덮지 않는다.

## 4. 유지할 규칙과 문서 충돌

### 변경하지 않을 기준

- 현재 플레이어는 백, 컴퓨터는 흑이다. 이번 UI 작업에 진영 선택 기능을 추가하지 않는다.
- 참가금은 각 50G, 한 판에 한 번만 낸다. 체스 40G / 포커 60G 배당, 체스 무승부 시 전체 100G 이월을 유지한다.
- 체스 배당은 확정만 하고 포커 후 지급한다. 금화 선택에서 이 금액을 재사용할 수 없다.
- 생존 카드 5장과 공개 순서를 선택한다. 베팅은 공개 1장·2장·3장 시점의 3라운드이며, 추가 공동 카드는 없다.
- 최소 정규 베트/인상은 라운드 시작 시 20G, 이후에는 직전 정규 인상폭 이상이다. 짧은 올인과 레이즈 권한 잠금을 유지한다.
- 쇼다운은 족보 → 랭크 → `♠ > ♥ > ♦ > ♣` 순이다. 합법적인 현행 포커에는 무승부가 없다.
- 폴드 후 남은 비공개 카드는 숨긴다. 미매칭 초과액은 반환한다. 정산은 한 번만 한다.
- 50G 미만은 다음 판 참가 불가, 정확히 50G는 참가 가능하다. 기본 자금·상대·AI 판단·캠페인 조건은 그대로다.
- 최근 사용자 요청대로 중단·새로고침은 현재 단계에서 이어한다. 이미 정산된 과거 도주 기록은 재계산하지 않는다.

### 구현 전에 정리해야 할 문서 불일치

| 위치 | 남아 있는 설명 | 이번 설계에서 따르는 기준 |

| `04_CHESS_SYSTEM.md`, `06_ECONOMY_SYSTEM.md`, `08_GAME_FLOW.md` 일부 | 종료하면 도주, 저장하고 메인으로 금지 | 최근 사용자 지시와 `main.tsx`의 저장·이어하기 구현 |

## 5. 화면마다 무엇을 보이게 할 것인가

| 장면 | 기본 표시 | 주 행동 | 눌러서 확인 |
|---|---|---|---|
| 메인 | 제목, 정원, 저장된 단계 한 줄 | 처음이면 게임 시작, 저장이 있으면 이어하기 | 새 게임·설정·도움말·기록 |
| 참가 준비 | 두 플레이어, 잔액, 50G, 내 잔액 변화 | `50G · 대국 시작` | 배당표·이야기 |
| 체스 | 8×8 판, 짧은 차례, 양측 금고 | 기물 탭 → 도착 칸 탭 | 선택 기물의 역할·카드, 잡은 카드, 수순 |
| 체스 종료 | 마지막 판 위 작은 결과 패널 | `포커로` | 판 다시 보기·종료 사유 |
| 패 선택 | 생존 카드, 선택 슬롯 1~5, 선택 수, 현재 족보 | `이 패로 시작` | 추천, 공개 순서 안내 |
| 포커 베팅 | 상대 패, 내 패, 팟, 내 금고, 콜 금액, 금화 줄, 행동 줄 | 체크/콜 또는 선택 금액 확정 | 상세 투입액·기록·족보표 |
| 공개 연출 | 한 장씩 드러나는 카드, 공개 위치 강조 | 지켜보기 / 건너뛰기 | 일시정지 |
| 승패 | 두 패, 포커 승리/패배, 비교 이유 한 줄 | `계속` | 족보 상세 |
| 정산 | 이번 판 순손익, 최종 금고 | 다음 대국 준비 / 조건에 따른 엔딩 | 세부 원장 |

**판에서 자주 쓰는 행동은 접지 않는다. 읽기 위한 정보만 접는다.** 레이즈·올인을 숨기는 현재 `더 베팅하기` 구조는 교체 대상이다.

## 6. 금화 베팅의 정확한 의미

### 6.1 금화를 누르면 무엇이 달라지는가

항상 보이는 금화: **`+10G` `+20G` `+50G` `+100G`**.

- 금화 클릭은 **더 올릴 금액 R**을 늘린다. 베팅을 즉시 실행하거나 금고를 차감하지 않는다.
- 처음에는 `R=0`. 필요한 콜 금액은 게임이 별도로 계산해 표시한다.
- 상대에게 맞춰야 하는 금액이 없으면 `이번 지불 = R`이다.
- 상대에게 40G를 맞춰야 하고 R을 50G 담았다면 `콜 40 + 더 올림 50 = 이번 지불 90G`이다.
- 숫자 입력창·모바일 숫자 키보드는 사용하지 않는다. 버튼과 준비된 금화 묶음으로 조절한다.
- 확정 전 받침과 실제 팟은 다른 위치다. 확정 전에는 팟 숫자도 변하지 않는다.

`+10G`는 10G 베팅을 허용한다는 뜻이 아니다. 최소 20G인 차례에 10G만 담으면 베팅 버튼은 비활성이고 받침 옆에 `10G 더 필요`가 보인다. 두 번 눌러 20G를 만들거나 `[최소]`로 맞춘다.

### 6.2 버튼 구성과 피드백

| 조작 | 동작 |
|---|---|
| +10 / +20 / +50 / +100 | 해당 인상액을 받침에 추가, 금화 묶음 수와 이번 지불액 갱신 |
| 최소 | 현재 정규 최소 인상폭으로 R을 설정. 이미 담은 값에 덧붙이지 않음 |
| 되돌리기 | 마지막 준비 조작 한 번 취소. 확정한 베팅은 취소하지 못함 |
| 비우기 | R=0, 준비된 올인 취소. 이미 낸 참가금·베팅은 변하지 않음 |
| 전부 | 남은 금고 전액을 **올인 준비**. 실제 올인은 별도 확정 버튼 |
| 준비 금액 탭 | 선택형 미세 조정판: `−1 / +1 / −10 / +10`, 빠른 금액 `최소 / 반 팟 / 팟`. 숫자 입력창 없음 |
| 체크 / 콜 | 준비 중인 금화를 버리고 해당 합법 행동만 확정 |
| 폴드 | 해당 판의 포커를 포기. 준비 금화는 버리고 남은 비공개 패 유지 |

금화는 숫자와 각인으로 구분한다. 색만 다른 카지노 칩으로 만들지 않는다. 예: 10G는 한 묶음, 20G는 두 겹, 50G는 작은 금화 더미, 100G는 묶음 표식을 쓰되 터치 영역은 동일하다. 이미지는 후속 제작이며 이번에는 ASCII 표기만 한다.

### 6.3 행동 줄은 세 자리로 고정

왼쪽 `[폴드]`, 가운데 `[체크]` 또는 `[40G 콜]`, 오른쪽 `[20G 베팅]` 또는 `[80G 내고 레이즈]`.

- 준비 전에는 체크/콜만 금색으로 강조한다. 유효한 인상 금액을 준비하면 오른쪽 확정 버튼을 금색으로 강조한다.
- 3개 버튼의 위치는 바꾸지 않는다. 마지막 순간에 체크 자리로 다른 행동이 이동하지 않게 한다.
- 준비 금액이 없거나 부족하면 오른쪽 버튼은 비활성이다. 이유는 가까운 받침에 한 줄만 표시한다.
- 상대 차례에는 조작이 잠기고 `상대 차례`를 표시한다. 자동 체크·예약 콜은 추가하지 않는다.
- 올인은 `[올인 · 950G]`라고 명시한다. 일반 베팅 버튼을 누르는 것만으로 남은 돈 전부가 조용히 선택되면 안 된다.

### 6.4 금액·권한 경계

1. **20G보다 큰 최소 인상:** 직전 정규 인상이 40G면 `[최소]`는 40G를 준비한다. +20G만 눌렀다고 합법으로 만들지 않는다.
2. **콜 포함:** 콜 40G + 최소 인상 40G면 이번 지불은 80G다. 버튼에 40G만 표시해서 80G를 차감하지 않는다.
3. **잔액 초과:** 담을 수 없는 금화는 비활성으로 둔다. 범위를 넘는 클릭을 몰래 올인이나 다른 금액으로 바꾸지 않는다.
4. **짧은 올인:** 일반 최소를 채울 수 없어도 엔진이 허용하면 `[전부]`로 정확한 잔액을 준비한다. 정규 레이즈로 우회하지 않는다.
5. **레이즈 잠금:** 짧은 올인 이후 레이즈 권한이 없다면 금화·정규 인상·불법 올인은 잠긴다. 합법 콜·폴드는 유지한다.
6. **1G 단위 보존:** 기존 엔진은 정수 금액을 허용한다. 기본 금화가 10G 단위라고 21G·35G 같은 합법 금액을 금지하지 않는다. `[최소]`와 1G 미세 조정, 10G의 배수가 아닌 잔액의 정확한 올인을 제공한다.
7. **큰 금고:** 반 팟/팟/전부는 준비 금액을 빠르게 설정하는 보조 선택이다. 포커 현재 팟 P만 기준으로 하고 체스 확정 배당은 포함하지 않는다. 반 팟은 `R=ceil(P/2)`, 팟은 `R=P`에서 시작해 최소 정규 인상 이상·`L-C` 이하로 맞춘다. 이 범위가 없으면 비활성이다. 이들은 **인상액 단축 선택**이며, 콜을 포함한 지불 D를 결과 버튼에 먼저 표시한다. 금화 버튼은 길게 눌러 준비액만 빠르게 늘릴 수 있지만 확정 버튼에는 자동 반복을 적용하지 않는다.
8. **상대보다 큰 금고:** 임의로 상대 잔액을 내 베팅 상한으로 만들지 않는다. 기존 엔진이 허용하는 금액을 유지하고 미매칭 반환을 정산에서 설명한다.
9. **판·차례·라운드 변경:** 준비한 금화는 초기화한다. 이전에 담은 금액이 다음 라운드에서 자동 제출되지 않는다.
10. **중단·저장:** 준비 중인 금화는 확정된 원장에 저장하지 않는다. 게임으로 돌아오면 실제 납부액은 그대로이고 준비 받침은 비어 있다.

어떤 선택 방식이든 `이번 지불 = 남은 금고`가 되면 확정 버튼은 반드시 `올인 · XXG`로 바뀐다. 현재 엔진의 올인 가능 여부를 다시 확인하고 `allin` 행동으로 보낸다. 금액을 조용히 잘라 맞추거나 일반 베팅 문구를 유지하지 않는다. 콜만으로 금고가 바닥나는 경우는 `XXG 콜 · 올인`으로 표시하고 기존 `call` 처리를 사용한다.

### 6.5 개발자용 변환 — 화면에는 누적 금액을 입력시키지 않는다

```text
Cw, Cb = 참가금을 포함한 현재 누적 납부액
Bw     = 이 판 시작 시 내 잔액
H      = max(Cw, Cb)
C      = max(0, Cb - Cw)             # 맞춰야 할 콜
L      = Bw - Cw                    # 지금 쓸 수 있는 금고
R      = 금화 버튼으로 고른 인상액
T      = H + R                      # 엔진이 받는 누적 목표액
D      = T - Cw = C + R             # 이번에 실제 내는 금액

정규 금액 후보: actions(g, 'w').raise && R >= lastRaise && D <= L
D < L이면: act(g, 'w', { type: 'raise', amount: T })
D == L이면: 올인 가능 여부를 확인하고 { type: 'allin' }

콜: actions(g, 'w').call이면 { type: 'call' }, 지불 = min(C, L)
올인: actions(g, 'w').allin이면 { type: 'allin' }, 지불 = L
짧은 올인은 일반 raise 호출로 보내지 않는다.
```

합법성은 기존 `actions()`와 `act()`가 최종 결정한다. UI가 새 베팅 규칙을 계산해 엔진을 대체하지 않는다. 단축값을 선택한 후에도 확정 직전에 현재 게임 상태로 다시 검사한다.

### 6.6 현재 엔진으로 검증한 예

일반 사례의 시작 잔액은 1,000G다. Cw/Cb에는 참가금이 포함된다.

| 현재 Cw / Cb | 최소 인상 | 선택 | 이번 지불 D | 엔진 목표 T | 기대 |
|---|---:|---|---:|---:|---|
| 50 / 50 | 20 | +20 | 20 | 70 | 정상, 금고 930 |
| 50 / 50 | 20 | +10만 | — | 60 | 정규 베팅 불가 |
| 50 / 90 | 40 | +40 | 80 | 130 | 콜40 + 인상40, 금고870 |
| 50 / 90 | 40 | +20만 | — | 110 | 최소 인상 미달 |
| 90 / 90 | 20 | +50 | 50 | 140 | 기존 납부액을 다시 내지 않음 |
| 50 / 50 | 20 | 1G 조정으로 +21 | 21 | 71 | 정수 금액 보존 |
| 50 / 50, 시작금65 | 20 | 전부 | 15 | 65 | 짧은 올인, 이미 행동한 상대의 레이즈 권한을 다시 열지 않음 |
| 50 / 90, 시작금65 | 40 | 콜 | 15 | 65 | 부족분 올인 콜, 상대 미매칭25 반환 |
| 50 / 50, 시작금87 | 20 | 전부 | 37 | 87 | 30/40으로 반올림하지 않음 |

위 금액 및 레이즈 잠금은 임시 검증 코드에서 현재 `src/engine.ts`를 직접 호출해 확인했다. 새 금화 UI가 구현되거나 사용성 검증을 마쳤다는 의미는 아니다.

## 7. 장면 구성과 반응형 기준

### 화면은 세 구역이 공간을 나눠 쓴다

```text
HUD     : 단계 / 차례 / 상대 / 메뉴
SCENE   : 체스판 또는 상대 패 - 중앙 받침 - 내 패
ACTION  : 선택 카드 확정 또는 금화 선택·행동 버튼
```

`ACTION`을 문서 하단에 두거나 `SCENE` 위에 겹쳐 고정하지 않는다. 실제 높이를 가진 행으로 예약하고 장면이 나머지 공간을 쓰게 한다. `100dvh` 또는 실제 visual viewport와 safe-area를 기준으로 계산한다.

| 환경 | 배치 |
|---|---|
| 모바일 세로 360~430px | 상대 위·내 패 아래·조작 맨 아래. 양쪽 5장 전부와 행동 줄이 동시에 보이는 것이 목표 |
| 작은 높이/320px | 캐릭터 장식의 점유 공간을 줄이고 카드 면 중심의 간결 모드. 금액·무늬·버튼 글자를 먼저 줄이지 않음 |
| 모바일 가로 | 왼쪽 장면 + 오른쪽 조작 서랍. 세로 화면을 그대로 축소하지 않음 |
| 1280×720 이상 데스크톱 | 넓은 중앙 장면, 하단 금화·행동바, 양옆 짧은 금고/HUD. 긴 사이드바 없음 |
| 글자 200% 확대 | 필요한 보조 패널의 내부 스크롤 허용, 행동 버튼을 잘라 숨기지 않음 |

- 모바일 금화 버튼은 최소 44×44px, 주 행동은 높이 48~56px. 4개 금화는 한 줄, 행동은 별도 줄에 둔다.
- 카드 정보와 행동 글자는 모바일 14~16px 이상을 목표로 한다. 보조 표식만 더 작게 쓴다.
- 색만으로 상태를 전달하지 않는다. `공개`, 잠금, 숫자, 기호를 함께 사용한다.
- 배경 위에 직접 작은 글자를 얹지 않고, 정보를 담는 부분에 차분한 단색 바탕을 둔다.
- 기본 플레이에서는 페이지 스크롤을 없애는 것을 목표로 한다. 생존 카드 목록·도움말·거래 기록은 자기 패널 안에서만 스크롤한다.
- 390×844 기준 초안 예산은 HUD44 + 상대정보28 + 상대패112 + 팟48 + 내패128 + 상태24 + 조작216 + 여백24 = 724px다. 작은 높이에서는 장식 전신을 생략한 카드 중심 표시로 공간을 확보한다. 실제 글꼴·safe-area를 포함한 브라우저 검증이 필요하다.

## 8. 미술을 유지하면서 읽히게 만드는 규칙

- **캐릭터:** 진영은 백/흑, 역할은 모자. 같은 진영 안에서 킹·퀸만 다른 색으로 보이지 않게 한다.
- **카드 면:** 공개 상태에서는 양쪽 모두 같은 밝기의 양피지 바탕. 하트·다이아 빨강, 스페이드·클럽 검정은 유지한다.
- **미공개:** 상대는 카드 뒷면, 나는 내용을 읽을 수 있는 약한 음영. 캐릭터 전체에 공개 여부용 흐림을 적용하지 않는다.
- **앞뒤:** 공개 카드는 약간 앞으로, 미공개는 약간 뒤로. 모든 카드의 숫자와 전체 면이 보이는 범위를 넘겨 이동하지 않는다.
- **선택:** 전신 확대보다 바닥 표시·금색 외곽선·공개 순서 번호로 구분한다. 확대해서 옆 카드를 가리지 않는다.
- **금화:** 현재 잉크선·해칭·탁한 금색을 사용한다. 준비 받침과 실제 팟의 위치·라벨을 분리한다.
- **자산 작업:** 이 단계에서는 새 그림을 만들지 않는다. 현재 자산을 배치할 영역과 필요한 표시 계층만 결정한다.

## 9. 클릭 이후의 반응과 긴장감

| 사건 | 피드백 / 권장 간격 | 원장 처리 |
|---|---|---|
| 금화 선택 | 80~150ms 안에 선택 표시, 작은 금화 한 번 이동, 이번 지불액 갱신 | 없음 |
| 베팅 확정 | 버튼 즉시 잠금 → 금고/팟 갱신 → 250~400ms 금화 이동 | 기존 엔진에 한 번만 전달 |
| 체크 | 짧은 표시·차례 이동, 금화 이동 없음 | 추가 지출 없음 |
| 다음 공개 라운드 | 새 공개 위치만 강조 후 다음 행동 열기 | 확정한 5장과 순서 유지 |
| 마지막 쇼다운 | 기존 0.9초 시작 대기 → 내/상대 남은 카드 교대로 약0.85초 → 마지막 카드 후1.2초 | 결과 저장은 이미 완료, 다시 지급하지 않음 |
| 승패 | `포커 승리` 또는 `포커 패배`, 양쪽 족보, 차이를 만든 정보 한 줄 | 계속 누르기 전까지 정산창 열지 않음 |
| 계속 | 순손익·최종 금고와 정산 상세 | 원장 읽기만 수행 |

타이밍은 사용자 테스트 후 조절할 제안값이다. 체스 시계나 베팅 제한시간을 추가하지 않는다. 임의의 생각 대사·캐릭터 반응이 상대의 숨은 패 강도를 암시해서도 안 된다. 사운드를 넣는 후속 작업은 기본 음량 조절·음소거·동작 줄이기를 지원한다.

## 10. 처음 플레이하는 사람에게 가르치는 방식

- 시작 전에 규칙 본문을 읽게 하지 않는다. `게임 시작 → 50G 대국 시작`의 두 번 선택으로 첫 체스판에 들어간다.
- 첫 체스 차례에 `기물을 고르고, 이동할 칸을 누르세요` 한 줄만 표시한다. 첫 합법 수 뒤에는 사라진다.
- 첫 패 선택에 `고른 순서대로 앞의 3장이 공개됩니다`와 슬롯 번호를 보여준다.
- 첫 베팅에 금화 줄을 한 번 강조하고 `금화를 고른 뒤 베팅`이라고 안내한다. 레이즈가 무엇인지는 해당 용어를 눌렀을 때 설명한다.
- 오류는 관련 위치에 붙인다. `최소 인상 40G`, `남은 금고 35G`, `지금은 상대 차례`처럼 행동에 필요한 이유만 말한다.
- 게임 이름·소제목·영어 장식·규칙 버전·개발 상황 안내를 같은 화면에 반복하지 않는다.

## 11. 구현 순서와 검증 기준

### 구현 순서

1. `actions()` 결과와 준비 금화를 연결하는 표시 계산을 먼저 만든다. 6.6의 금액을 테스트로 고정한다.
2. 숫자 입력과 숨겨진 레이즈 영역을 금화 줄·준비 받침·항상 보이는 행동 줄로 교체한다.
3. HUD / 장면 / 행동 영역이 겹치지 않게 공간을 예약한다. 모바일과 데스크톱에 같은 의미·다른 배치를 적용한다.
4. 패 선택 슬롯·체스 선택 정보·짧은 처음 안내를 정리한다.
5. 공개·승패·정산을 연결하고, 마지막에 금화·소리·짧은 강조를 다듬는다.

게임 엔진, AI, 정산식, 저장 데이터 버전은 유지한다. UI 내부의 받침 상태와 표시 컴포넌트 분리는 화면 구현 범위이며 게임 구조 전면 개편을 요구하지 않는다. 기존 스타일 끝에 전역 보정을 계속 추가하기보다 바꾸는 장면의 오래된 규칙을 정리하고 장면별 범위를 명확히 한다.

### 수용 기준 — 구현 후 확인할 항목

- [ ] 320/360/390/430px 세로, 844×390 가로, 1280×720·1920×1080에서 내 패·상대 패·팟·주 행동이 가려지지 않는다.
- [ ] 모바일·데스크톱 베팅에 숫자 입력창이 없고 모바일 키보드가 열리지 않는다.
- [ ] 금화 클릭만으로 금고·팟·게임 상태·상대 차례가 바뀌지 않는다.
- [ ] 최소 베팅은 `[20G] → [20G 베팅]` 두 번으로 가능하다. 체크/콜은 한 번이다.
- [ ] 콜40 + 인상40은 버튼에 이번 지불80을 표시하고 실제로80만 차감한다.
- [ ] 10G 단독 불가, 인상폭40, 짧은 올인15, 정확한 올인37, 1G 조정, 잔액초과, 레이즈 잠금을 확인한다.
- [ ] 2연타·길게 누르기·상대 응답·라운드 변경 중에 행동이 중복 실행되거나 예약되지 않는다.
- [ ] 준비 금화가 있는 채로 메뉴/재시작/이어하기를 사용해도 확정된 게임만 복원한다.
- [ ] 폴드 시 남은 상대 패를 공개하지 않는다. 쇼다운 건너뛰기는 승패 화면에서 멈추며, 계속을 눌러야 정산창을 연다.
- [ ] 밝은/어두운 진영 모두 공개 카드 면의 대비가 같고, 미공개 처리는 카드 면에만 적용한다.
- [ ] 키보드·터치·동작 줄이기·큰 글자에서도 같은 행동을 할 수 있다.
- [ ] 새 플레이어 3~5명 관찰: 긴 설명 없이 시작, 첫 이동, 20G 베팅, 40G 콜, 폴드를 찾는지 확인한다. ‘3초 안에 다음 버튼 찾기’는 목표이지 현재 검증 결과가 아니다.
